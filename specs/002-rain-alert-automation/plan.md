# Implementation Plan: Rain Alert Automation

**Branch**: `002-rain-alert-automation` | **Date**: 2026-05-10 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/002-rain-alert-automation/spec.md`

---

## Summary

A single Azure Logic Apps (Consumption plan) workflow (`la-darkfactory-rain-alert`) that runs every 5 minutes, calls the Open-Meteo API for current and 48-hour forecast weather data, and sends private Teams messages to the administrator when rain is detected or forecast. Alert suppression state persists in a dedicated `DarkFactory-AlertState` SharePoint list. All configuration is read from the existing `DarkFactory-Settings` list (extended with four new `Alert.*` keys). The Logic App uses only standard (non-premium) connectors for SharePoint and Teams, plus the free built-in HTTP connector for the Open-Meteo API.

## Implementation Phases

### Phase 1 — Infrastructure Foundation (Day 1)

**Goal**: Azure resource group, Logic App created with connections authorised; SharePoint data ready. No workflow logic yet.

#### 1.1 Azure infrastructure
- Create ARM template `connections/sharepoint-connection.json` and `connections/teams-connection.json`

- Authorise SharePoint and Teams connections in Logic App designer (admin OAuth, one-time)

#### 1.2 SharePoint data provisioning

  - Add `Alert.*` rows to `DarkFactory-Settings`
  - Create `DarkFactory-AlertState` list with `LastSentAt` DateTime column
  - Seed `ForecastRain` and `CurrentRain` items
- Run script against DarkFactory site

**Deliverable**: Azure resources exist, connections authorised, SharePoint lists ready. Logic App has empty workflow (disabled).

### Phase 2 — US2: Current Rain Alert (Days 1–2)

**Goal**: Real-time rain detection working end-to-end. Simpler than forecast (no array iteration) so built first to validate the full pipeline.

**User story**: US2 (P2 in spec) — implemented first because it validates the full pipeline (API → SharePoint read → condition check → Teams message → state update) with the simplest logic.

#### 2.1 Logic App workflow scaffold (`logic-app-definition.json`)
- Recurrence trigger: every 5 minutes
- Initialize Variable: `rainCodes` (array: `[51,53,55,56,57,61,63,65,66,67,80,81,82,95,96,99]`)
- Initialize Variable: `wmoLabels` (object: WMO code → human label map from data-model.md)
- HTTP action: GET Open-Meteo with `current=weather_code,temperature_2m&hourly=weather_code,time&forecast_days=2&timezone=auto`
- Parse JSON: parse Open-Meteo response against WeatherApiResponse schema
- Get items (SharePoint): `DarkFactory-Settings` with OData filter for `Weather.*` and `Alert.*` keys
- Get items (SharePoint): `DarkFactory-AlertState` (all items, no filter)

#### 2.2 Current rain branch
- Extract `Alert.CurrentRainSuppressionHours` and `Alert.RecipientId` from settings response
- Find `CurrentRain` item from AlertState response; extract `LastSentAt`
- Condition (null-safe): `if(equals(lastSentAt, null), true, less(addHours(lastSentAt, suppressionHours), utcNow()))`
  - True (suppression expired or first run):
    - Condition: `contains(variables('rainCodes'), body('Parse_Weather')['current']['weather_code'])`
      - True (raining now):
        - Post Teams message (current rain format — see data-model.md)
        - Update item (SharePoint): `DarkFactory-AlertState` → CurrentRain → `LastSentAt = utcNow()`
      - False: no action
  - False (within suppression window): no action

**Deliverable**: Current rain alerts delivered within 5 minutes. Suppression prevents duplicate alerts. Run history shows correct pass/fail.

### Phase 3 — US1: Forecast Rain Alert (Days 2–3)

**Goal**: Forecast rain detection added as a parallel branch to the same Logic App workflow.

#### 3.1 Forecast rain branch (parallel to current rain branch)
- Extract `Alert.ForecastSuppressionHours` from settings
- Find `ForecastRain` item from AlertState; extract `LastSentAt`
- Condition (null-safe): `if(equals(lastSentAt, null), true, less(addHours(lastSentAt, suppressionHours), utcNow()))`
  - True (suppression expired or first run):
    - Parse current local hour from `body('Parse_Weather')['current']['time']` using `int(formatDateTime(..., 'H'))`
    - Compose: slice `hourly.weather_code` array from index `[current_hour]` to `[47]` using `skip(hourly_codes, current_hour)`
    - Filter array (built-in, free): filter the sliced array where `contains(variables('rainCodes'), item())` — returns only rain-code entries
    - Condition: `length(body('Filter_Forecast_Rain')) > 0`
      - True:
        - Set variable `forecastRainCode` = first element of filtered array
        - Post Teams message (forecast rain format — see data-model.md)
        - Update item (SharePoint): `DarkFactory-AlertState` → ForecastRain → `LastSentAt = utcNow()`
  - False (within suppression window): no action

**Design note** (from consultant review): Use the Logic Apps built-in **Filter array** action instead of For Each. A For Each over 48 items generates 48 billed actions per run ($0.35/day extra); Filter array is a single free built-in action. The Filter array approach also avoids the For Each "no native break" limitation.

**Deliverable**: Forecast rain alerts delivered. Both branches run in parallel after the shared API call and settings read. End-to-end pipeline confirmed.

---

### Phase 4 — US3: Reliability and Error Handling (Day 3)

**Goal**: Error handling configured; run history confirmed; recovery behaviour verified.

#### 4.1 Scope + Catch error handling
- Wrap all post-trigger actions in a Scope named `Main`
- Add a Catch scope (run after `Main` with status `Failed`): log a note to run history (no additional action needed — Logic Apps run history already captures failure details)
- Set HTTP action retry policy: 3 retries, exponential backoff, max 600s interval
- Set SharePoint and Teams actions retry: 2 retries, fixed 30s interval

#### 4.2 Run history retention verification
- Confirm Logic Apps Consumption plan retains run history 90 days (default) — exceeds FR-011 requirement of 30 days
- No additional configuration needed

#### 4.3 Recovery test
- Temporarily configure an invalid Open-Meteo URL → confirm run fails gracefully (no crash, no Teams message, next run proceeds normally)
- Restore correct URL → confirm next run succeeds

**Deliverable**: Error handling confirmed. Run history shows clear pass/fail state. Recovery from API failure verified within one polling cycle.

## Key Design Decisions (SOLID/DRY reference)

| Decision | Principle | Rationale |
|---|---|---|
| One Logic App, two parallel branches | S (Single Responsibility) | One workflow per concern: forecast check and current rain check are independent but share the same API call |
| `rainCodes` variable defined once at workflow start | DRY | Single source of truth for rain WMO codes; both branches reference the same variable |
| All config from DarkFactory-Settings | DRY | No hardcoded values in the Logic App definition; config changes take effect on next run |
| SharePoint AlertState for suppression state | L (Liskov) | Consistent data contract: both branches read/write the same AlertState schema |
| Parallel branch structure | O (Open/Closed) | New alert types (e.g., extreme heat) can be added as new parallel branches without modifying existing branches |
| Scope + Catch error handling | S (Single Responsibility) | Error handling is a single catch-all; individual steps focus on their logic only |
| No retry loop within a single run | YAGNI | Logic Apps built-in retry policies on HTTP/connector actions handle transient failures; next scheduled run handles persistent failures |
